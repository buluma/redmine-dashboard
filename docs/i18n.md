# Internationalization (i18n)

Converge supports multiple languages for its user interface, allowing global teams to use the application in their preferred language.

## Supported Languages

| Locale | Language  | Region                   |
| ------ | --------- | ------------------------ |
| `en`   | English   | United States (default)  |
| `ru`   | Russian   | Russia                   |
| `uk`   | Ukrainian | Ukraine                  |
| `af`   | Afrikaans | South Africa             |

Only these 4 have a `messages/*.json` file and are loaded by `I18nProvider.tsx` today. See [Adding a New Language](#adding-a-new-language) below for the steps to add another (e.g. Spanish, German, French — not currently supported despite what an earlier version of this doc claimed).

## Architecture

Converge uses a **client-side i18n approach** (no URL prefixes or server-side routing):

1. All 4 language files are loaded on app initialization
2. Locale is stored in `localStorage` (`converge-locale`)
3. Translation function is available via `useI18n()` hook
4. No page reload required when switching languages

## Directory Structure

```
messages/
├── en.json    # English (default, reference translations)
├── ru.json    # Russian
├── uk.json    # Ukrainian
└── af.json    # Afrikaans
```

### Using the `t()` Function

This section details how to use the `t()` function for translations, including interpolation and pluralization.

#### Variable Interpolation

```tsx
// messages/en.json
{
  "greeting": {
    "user": "Hello, {name}!"
  }
}

// In component:
t("greeting.user", { name: "Alex" }) // Output: Hello, Alex!
```

#### Pluralization

For strings that need to change based on a count (e.g., "1 issue" vs. "2 issues"), use the `count` variable and define `one` and `other` keys in your translation object. The `t()` function will automatically select the correct form based on the `count` value.

```tsx
// messages/en.json
{
  "issues": {
    "count": {
      "one": "{count} issue",
      "other": "{count} issues"
    },
    "acrossIssues": "{count} chat messages across {issueCount} {issueCount, plural, one {issue} other {issues}}"
  }
}

// In component:
// For singular:
t("issues.count", { count: 1 }) // Output: 1 issue

// For plural:
t("issues.count", { count: 5 }) // Output: 5 issues

// For multiple variables and pluralization:
// Note: The primary pluralization is based on 'count'. Other variables like 'issueCount' are interpolated afterwards.
t("issues.acrossIssues", { count: 3, issueCount: 5 }) // Output: 3 chat messages across 5 issues
t("issues.acrossIssues", { count: 1, issueCount: 1 }) // Output: 1 chat message across 1 issue
```

The `t()` function automatically handles selecting the correct plural form based on the `count` variable passed. If `count` is 1, it uses the `one` translation; otherwise, it uses `other`. Other variables (like `issueCount`) are interpolated after the plural form is selected.

### With Fallbacks

```tsx
// If the key doesn't exist, fall back to a default string
t("nonexistent.key", "Default fallback text");

// Variable interpolation + fallback
t("greeting.user", { name: "Alex" }, "Hello");
```

### With Navigation

```tsx
// Use translation keys in navigation
<Link href="/dashboard">
  {t("nav.dashboard")}
</Link>;
```

## Adding a New Language

### Step 1: Create the Translation File

1. **Add New Keys to `en.json`:** Define all new translation keys in `messages/en.json` first. This serves as the reference.
2. **Backfill Other Locales:** Use the script `bun run i18n:fill-missing` to automatically copy all keys from `en.json` into the newly created or existing locale files (e.g., `es.json`, `de.json`). This ensures all keys exist in every locale, preventing runtime errors.
3. **Translate:** Manually translate the backfilled English strings in each locale file.

Example for Portuguese (`pt.json`):

```json
{
  "common": {
    "save": "Salvar",
    "cancel": "Cancelar",
    "delete": "Excluir"
  },
  "dashboard": {
    "title": "Painel",
    "openIssues": "Issues Abertos"
  }
}
```

### Step 2: Add Locale to the Loader

Update `src/components/I18nProvider.tsx` — `en` is preloaded separately at module scope, so `locales` here lists the *other* languages `loadAllMessages` dynamically imports:

```tsx
const loadAllMessages = async () => {
  const locales = ["ru", "uk", "af", "pt"]; // Add new locale
  for (const locale of locales) {
    try {
      const msg = await import(`../../messages/${locale}.json`);
      translations[locale] = msg.default || msg;
    } catch (err) {
      console.error(`Failed to load locale: ${locale}`, err);
      translations[locale] = translations.en;
    }
  }
};
```

### Step 3: Add to Language Switcher

Update `src/components/LanguageSwitcher.tsx` — entries use `label` and an optional `flag`, not `name`, and the `Locale` type union needs the new code too:

```tsx
type Locale = "en" | "ru" | "uk" | "af" | "pt";

const languages = [
  { code: "en" as const, label: "English", flag: "🇺🇸" },
  { code: "ru" as const, label: "Русский", flag: "🇷🇺" },
  { code: "uk" as const, label: "Українська", flag: "🇺🇦" },
  { code: "af" as const, label: "Afrikaans", flag: "🇿🇦" },
  { code: "pt" as const, label: "Português", flag: "🇵🇹" }, // Add new language
];
```

## Translation File Format

All translation files follow a **nested object structure**:

```json
{
  "common": {
    "loading": "Loading...",
    "save": "Save"
  },
  "dashboard": {
    "title": "Dashboard",
    "stats": {
      "open": "Open Issues",
      "closed": "Closed Issues"
    }
  },
  "nav": {
    "dashboard": "Dashboard",
    "groups": {
      "personal": "Personal",
      "teamOps": "Team Ops"
    }
  }
}
```

### Accessing Nested Keys

```tsx
const { t } = useI18n();

// Nested: common.loading
t("common.loading");

// Nested: dashboard.stats.open
t("dashboard.stats.open");
```

## Language Switcher

The language switcher is available in the sidebar navigation and displays:

- Current language code (e.g., "EN")
- Dropdown list of available languages
- Persists selection in `localStorage`

### Manual Locale Switching

```tsx
import { useI18n } from "@/src/components/I18nProvider";

export function LanguageSelector() {
  const { locale, setLocale } = useI18n();

  return (
    <select value={locale} onChange={(e) => setLocale(e.target.value)}>
      <option value="en">English</option>
      <option value="ru">Русский</option>
    </select>
  );
}
```

## Development Guidelines

### 1. Always Use Translation Keys

**Don't:**

```tsx
<h1>Dashboard</h1>; // Hardcoded string
```

**Do:**

```tsx
<h1>{t("dashboard.title")}</h1>; // Translation key
```

### 2. Keep Keys Consistent

Follow the existing structure:

- `common.*` - Shared UI elements
- `dashboard.*` - Dashboard-related text
- `nav.*` - Navigation labels
- `form.*` - Form labels and messages

### 3. Handle Missing Translations

The fallback system ensures keys always return text:

- If a translation is missing, it falls back to English.
- If the key doesn't exist, it returns the key itself.
- `t()` supports either `t(key, fallback)` or `t(key, variables, fallback)`.

### 4. Test New Translations

After adding translations:

1. **Use the language switcher:** it's the permanent `LanguageSwitcher` component in the sidebar navigation (not a temporary one in `app/layout.tsx`) — switch locales there to test.
2. Navigate through all pages.
3. Verify all text is translated.
4. Check for missing keys (they will appear as `key.name`).

## Troubleshooting

### Translations Not Loading

1. Check browser console for import errors.
2. Verify the JSON file exists in `messages/`.
3. Ensure the locale is added to `I18nProvider.tsx`.

### Language Not Persisting

1. Check browser console for `localStorage` errors.
2. Verify cookies aren't blocking local storage.
3. Try incognito mode to isolate issues.

### Key Returns as Plain Text

If you see `some.key.name` instead of translated text:

- The translation file may be missing the key.
- Add the key to the appropriate language file.
- Or add a fallback: `t("some.key.name", "Default text")`

### Run Locale Coverage Audit

Use the built-in audit to compare every locale against `messages/en.json`:

```bash
bun run i18n:audit
```

It reports:

- JSON parse errors
- Missing keys by locale
- Extra keys that don't exist in English

### Fill Missing Keys Automatically

When you add new keys in `en.json`, you can backfill all locale files with English fallbacks:

```bash
bun run i18n:fill-missing
```

Recommended sequence:

1. `bun run i18n:fill-missing`
2. `bun run i18n:audit`
3. Replace the backfilled English strings with real translations per locale

### Removing Orphaned Strings

After migrating hardcoded strings to translation keys, some keys might become unused. To identify and remove them:

1. Run `bun run i18n:audit`. This tool helps find missing keys and extra keys that don't exist in English.
2. Manually review the output for keys that are not present in the codebase.
3. Remove orphaned keys from translation files.
